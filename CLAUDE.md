# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A custom French-language Foundry VTT game system (`id: "rpg"`, system.json), built on the ApplicationV2 / DocumentSheetV2 / HandlebarsApplicationMixin APIs introduced in Foundry V13. `system.json`'s `compatibility` block is `{ minimum: "13", verified: "14" }` — the live world now runs on Foundry V14, so V13 is a supported floor, not the active target; don't assume V13-only behavior when debugging something reported from the actual running world. No build step: pure ES modules loaded directly by Foundry (`esmodules: ["module/init.js"]` in `system.json`), no bundler, no `package.json` scripts. `node_modules/handlebars` at repo root exists only to validate templates locally (see Verifying changes below).

## Verifying changes (no build, no test suite)

There is no bundler and no test runner. Before considering a change done, run these checks — they catch the two classes of errors `node --check` misses: link-time failures (duplicate exports, bad imports) and template syntax errors.

**1. Every module loads without throwing** — write a throwaway ESM harness that stubs the Foundry globals and imports every file under `module/`:
```js
// stubs: foundry, game, CONFIG, CONST, Hooks, ui, canvas, Actor, Item, Combat, Combatant,
// ChatMessage, Roll, Dialog, RollTable, Macro, JournalEntry, Scene, Token, TokenDocument,
// fromUuid, fromUuidSync, loadTemplates, renderTemplate, getDocumentClass, Handlebars, PIXI
// (a Proxy that is callable/constructible/indexable works for all of them)
// then: for f of walk("module") -> await import(pathToFileURL(f))
```
A module that throws at import time (e.g. two files declaring the same top-level name) is otherwise invisible until Foundry loads it in-browser.

**2. Every `.hbs` template compiles**: `Handlebars.precompile(fs.readFileSync(path, "utf8"))` for each file under `templates/`.

**3. `system.json` and `template.json` are valid JSON** (`python3 -c "import json; json.load(open('...'))"`) — hand-editing `template.json` to add a schema field is common and easy to break.

Do all three from the repo root; there's no reason to scaffold this outside it.

## Architecture

### The permission model is the hard part

Most bugs in this codebase are permission bugs, not logic bugs: an action *works* for the GM and silently does nothing for a player. Two mechanisms enforce this and both are easy to defeat by accident:

- **`preUpdateItem` / `preUpdateActor` hooks in `init.js`** whitelist which dot-paths a non-GM write may touch (`system.equipe`, `system.cooldown.restant`, etc.). Foundry returns `false` from the hook to silently reject the whole update — no error, no partial write. When a player-facing feature "does nothing," check this whitelist first. Foundry itself injects bookkeeping keys into the payload (`_id` on `updateEmbeddedDocuments`, `_stats`, `sort`, `flags.*`, and `type` when unchanged) — the filter must ignore these rather than compare every key literally, or **every** grouped write from a player fails at once. See the `isBookkeeping` predicate in `init.js` for the current set.
- **Sheet-side view mode**: every sheet's `_onRender` checks `game.user.isGM` and, if false, disables every `input/select/textarea` in the content region (never the window header — that's where Close/Pin live) via `sheetContent()` / `sheetActionButtons()` in `sheets/sheet-helpers.js`. Any handler a player needs (declare a spell, change an equipment slot) must be bound **before** this early return, and any control the player is allowed to touch must be explicitly exempted from the blanket disable.

A hook's rejection is silent by design — when debugging a "nothing happens" report, log the rejected keys rather than guessing.

### `game.rpg.*` is the module→macro bridge

Macros (`module/macro/*.js`) are plain scripts installed as Foundry `Macro` documents — not compendium entries — in world folders "Macros système"/"Macros système (MJ)". The installer is inline in `init.js`'s `init` hook (no separate `auto-install.js` file despite what a stale comment elsewhere might suggest): it fetches each file's source over HTTP and creates/updates a world `Macro` per row of the `MACRO_DEFS` array (name/file/icon/scope). Every macro it creates carries `flags.rpg.systemMacro: true`, which a follow-up pass uses to delete any of *our own* previously-installed macros whose name is no longer in `MACRO_DEFS` (a renamed or retired entry — e.g. a dropped "Terrain (MJ)" macro — otherwise leaves orphaned copies in the world forever, since the per-entry loop only ever looks at *current* names and never notices a name that vanished from the list entirely). They are **not** ES modules and cannot `import`. Anything a macro needs from `module/rules/*` must be exposed on the `game.rpg` namespace during `init.js`'s `ready` hook (e.g. `game.rpg.combat`, `game.rpg.ranges`, `game.rpg.chat`, `game.rpg.defaultActions`). When adding a rule module a macro will call, remember to attach it to `game.rpg` — importing it directly from a macro file will fail silently at runtime.

### Derived stats: one function, one direction

`RPGActor.prepareDerivedData()` in `documents/actor.js` is the single source of truth for every computed stat (effective principales, defenses, fatigue max, pods/carry capacity, epuisement/exhaustion state, etc.). It reads `system.base.*` plus equipment/effect bonuses and writes `system.derived.*`. Sheets and rules read `system.derived.effective.*` — never recompute a formula in a sheet or macro. If a stat looks wrong, this file is where the bug almost always is, not in the sheet displaying it.

### Combat resolution is declare → GM-validate → resolve, always in that order

For both spells (`rules/spells.js`) and weapon attacks (`rules/attack-declare.js` + `rules/attack-resolve.js`): the player's action posts a chat message with the roll and a set of GM-only buttons (Échec/Réussite/Critique/Échec Critique). Only after the GM clicks does damage actually get rolled — `resolveDeclaredSpellFromMessage` / the attack-resolve equivalent. Never short-circuit this to apply damage at declaration time; the whole flow (fatigue cost, cooldowns, action budget consumption) is wired to fire at resolution, not declaration. For weapon attacks specifically, `resolveAttack` in `attack-resolve.js` rolls and posts the damage dice (visible chat rolls, one per die — main/crit/offhand) right away but does **not** touch the target's PV yet: it posts an `attackDamagePending` message with a MJ-only "Appliquer les dégâts" button, and only `applyAttackDamage` (bound alongside `bindAttackChatButtons`) actually decrements PV and fires weapon on-hit effects, once the MJ has seen the rolled numbers and confirms. Spells still apply damage in the same click as the verdict (`resolveDeclaredSpellFromMessage`) — this two-step split is attack-only for now.

- **`computeTN` in `rules/combat.js`** is the single seuil-de-touché (target number) formula: `TN = tnFromRatio(atk/def stats) + difficulté − bonus de toucher`, clamped to `[6, 16]`. Difficulty is *not itself* the TN — always route a forced/overridden difficulty back through `computeTN`/`applyDifficulty` rather than adding it to `tnFinal` after the fact, or you bypass the clamp and the friendly-target branch.
- **Friendly/self targets skip the stat comparison entirely** (`isFriendlyTarget`, keyed off token disposition): the difficulty field on the item *is* the TN outright, and `0` means automatic success. This only applies when the target is an ally or the caster themself — don't reuse this branch for hostile targets.
- **An attack's actors are resolved by UUID, never by id.** A monster on a scene is an *unlinked* token, whose synthetic actor carries its own PV/states/items but the **same `id`** as its prototype in the actors directory — so `game.actors.get(id)` silently returns the prototype. The whole attack chain used ids, and the reported symptom was exact: "Appliquer les dégâts" drained the monster's *sheet* while the token on the map kept full PV. `declareAttack` now records `actorUuid`/`targetUuid` alongside the ids, `resolveAttack`/`rollAttackDamage`/`applyAttackDamage`/`rollAttackDie` go through `resolveDeclaredActor(uuid, fallbackId)` (`attack-declare.js`), and the opportunity-attack buttons carry `data-enemy-uuid`/`data-mover-uuid` for the same reason. The id stays written and is still used as a fallback, so messages posted before this keep resolving. The spell flow already did this with `tokenUuid` — anything new that stores "which actor" in a chat message must store the UUID, not the id.
- **Chat visibility** (`rules/chat-visibility.js`): `.rpg-gm-only` spans are stripped from the DOM for non-GMs, `.rpg-hp-secret` spans are stripped unless the viewer owns the referenced actor **or** the referenced actor is a monster with `system.pvReveal === "exact"` (`pct` only unlocks the rounded percentage on the monster sheet itself, per `monster-sheet-v2.js` — chat lines are always exact numbers, so `pct` alone must not unlock them). Both hooks run in `renderChatMessageHTML`. Anything revealing a verdict before GM validation, or an enemy's exact HP/mana/fatigue, must go through one of these wrappers (`gmOnly()` / `hpSecret()`), not be written to raw chat content — this is easy to miss on ambient messages that don't look like "combat" (turn-start DOT ticks in `turn-effects.js`, the per-turn regen message in `init.js`'s `updateCombat` hook), not just the attack/spell resolution flow.

### Elemental resistances are a SECOND mitigation layer, and `resistances.js` is not the one that does it

Two unrelated things in this codebase are called "résistance", and confusing them is the easy mistake:

- **`rules/resistances.js`** — resistance to **états** (a burn lasts fewer turns, a poison ticks for less). Fields `durationReduction` / `dotReductionPct` / `immune`, stored per-item in `system.resistances[]` (a list of `{tag, effectKey, …}` rows) and per-state in `state.resistance`. Untouched by damage.
- **`rules/damage-types.js`** — resistance to **dégâts directs** (a sword blow, a fireball, a trap). One flat percentage per type, stored as a map `system.resistancesElem = {feu: 30, glace: -25, …}`. This is the newer half and the one everything below is about.

`DAMAGE_TYPES` in `damage-types.js` is the single ordered list of types — the same key namespace as `EFFECT_TAGS` (`feu`, `eau`, `eclair`, `glace`, `air`, `terre`, `lumiere`, `obscurite`) **plus `physique` and `magique`**, which are types in their own right: a weapon carries no element, so without them "resistant to physical" could not be expressed at all, and every armor-piercing monster concept was unreachable. `neutre` is deliberately *not* in the map — it means "no element", not "a type nobody resists". Every `<select>` offering a type builds its options from this map (spell `system.tag`, weapon `system.tag`, zone `system.damageTag`, the spell effect's `resistTag`); a new hardcoded element list anywhere is how "Physique" ends up existing in one dropdown and not the next.

- **`resolveDamageType({tag, livraison})` decides which resistance applies, and the fallback is the load-bearing part.** An explicit element wins; `neutre`/empty/unknown falls back to the **livraison** (`physique`/`magique`). That fallback is what makes a physical resistance bite on a plain sword and a magical one on an untagged spell — without it, `physique`/`magique` would sit in the dropdown and never match anything. Note this means livraison now does two jobs: it still picks *which defense absorbs* (armure vs résistance fixe/score) and it *also* names the type when nothing better is available.
- **The two layers apply in order, and only the first has a floor of 1.** `computeFinalDamage` (`combat.js`) runs armour/résistance (`mitigateDamage`, min 1, capped at 70%) and *then* the elemental percentage. Applying the floor again after the elemental step would make 100% resistance deal 1 damage — an immunity that isn't one. Bounds are `[-100, +100]`: 100 = immunity, negative = **vulnerability** (damage increased), which is why every display writes the sign explicitly (`resistRows()` precomputes the `text`, since Foundry ships no `abs` Handlebars helper).
- **`derived.resistancesElem` is where the total lives** — `prepareDerivedData` in `actor.js` sums the actor's innate map + every equipped weapon/armor/relic's `system.resistancesElem` + every active state's `resistance.damagePct`, clamped once at the end. Monsters keep their standing exclusion from equipment bonuses, so theirs is innate + states only. Read this, never re-add the pieces at a call site.
- **Every surface that describes a resistance goes through one formatter.** `resistTextParts()` in `damage-types.js` (plus its two adapters `fxResistTextParts` for a spell-sheet effect and `stateResistTextParts` for an actor's active state, which exist only because those two carry the same data under different field names) is what the spell sheet's effect header, `buildSpellEffectsPreview` in `spells.js`, and `decorateStates` in `character-sheet-v2.js` all call. The monster sheet used to hand-roll its own copy of `decorateStates` — same stat labels, but frozen at the day it was written, so it silently missed everything added since; it now calls the shared one, and a new state-describing surface must too. Equipment-side état-resistances are formatted by `gearStateResistRows` in `resistances.js` (which delegates to the same `resistTextParts`) and are now readable by the *player* on the weapon/armor sheets — the grid stays GM-only, but a wearer who cannot read what their own armor grants might as well not have it.
- **Four damage paths had to be updated, and a fifth would be silently un-resisted.** `computeFinalDamage` (zones/pièges), `RPGItem#rollDamage` (weapons) and `#_rollSpellDamage` (monster skills) apply it inline; the spell flow snapshots `elemPct` per damage block in `spells.js` at resolution time and `init.js`'s `.rpg-dmg-roll-btn` handler applies it when the player rolls — that split exists because the numbers are frozen before the dice are thrown, so a new damage path that computes its own mitigation must remember this layer or it just won't have it.
- **A spell grants resistance through an effect, and the damage half and the état half are two independent fields with two independent target types.** Section 6 of the spell sheet (`resistDamageTag` + `resistDamagePct`) writes `state.resistanceDamage = {tag, pct}`, read only by `sumStateResistances` in `actor.js`; section 7 (`resistTag` + `resistDurationReduction`/`resistDotPct`/`resistImmune`) writes `state.resistance`, read only by `resistances.js`. They deliberately do **not** share a tag: reducing fire *damage* has nothing to do with shortening *brûlures*, and an earlier version that folded both into one `resistance` object with a single element selector made one impossible without the other. `resistImmune` likewise covers états only — full damage immunity is `resistDamagePct: 100`. Same split on the equipment sheets: `system.resistancesElem` (damage, one % per type) beside `system.resistances[]` (états). Monsters get theirs from `system.gen.bands.<lvl>.resistancesElem.<type>` = `[min, max]` ranges rolled by `monster-gen.js`; a `[0, 0]` range (or an absent one) writes **nothing**, on purpose, so a hand-typed value on the sheet survives a re-roll.

### Action economy: budget slots, not free-form

`rules/action-budget.js` tracks a per-combatant, per-round budget (`slotsTotal.max = 2`) with named slots (`attaque`, `sortNormal`, `sortRapide`, `deplacement`, `recuperation`, `echangeArme`), each independently capped, stored as a combat flag (`getBudget`/`saveBudget`/`canUseSlot`/`reserveSlot`/`confirmSlot`). Fatigue-per-action is a *separate* concern from slot consumption — `actionFatigueCost(slot)` reads world settings (`fatigueAttaque`, `fatigueDeplacement`, `fatigueEchangeArme`), defaulting attack to 1 and movement/weapon-swap to 0, but a weapon's own `system.fatigueCost` field overrides the setting when present. Fatigue itself is **not capped at its max** (`prepareDerivedData` in `actor.js`) — the max is an exhaustion *threshold*, not a storage ceiling, so overshooting it is meaningful and must climb back down through it.

**A budget write is a write to the Combat document, which players are not allowed to make.** Foundry only lets a non-GM update a Combat's turn/round — never its flags, and `flags.rpg.budget`/`flags.rpg.log` are where the whole action economy lives. `movement-tracker.js` respects this (every budget write sits behind `if (!game.user.isGM) return;`) and `default-actions.js`'s "Changer d'arme" says so in a comment, but `macro/menu.js` did not: it reserved the slot *before* declaring, on the clicking client, so on a player's client the reservation threw and the `catch` swallowed the entire action — attack, spell, récupération and déplacement alike produced only an "Erreur …" toast and nothing was ever declared. Budget writes there are now wrapped in `budgetWrite()`, which logs and continues: the declaration goes out, the GM sees it and validates it. Anything new that writes the budget from a player-reachable path must do the same (or be moved GM-side) — and note the remaining gap this leaves: a slot a player could not reserve is not counted until the GM's own client confirms it.

### Every actor gets baseline "spell" items, not hardcoded actions

`rules/default-actions.js` grants every `character`/`monster` a small set of always-available actions (Repos, Attaquer, Changer d'arme, Retirer un état), implemented as real `type: "spell"` items so they get chat declaration, GM validation, action-budget integration, and hotbar drag-for-free. Attribution happens on `createActor` and via a version-gated backfill (`backfillDefaultActions`, called from `ready`) for actors created before a given action existed — bump the module's internal `VERSION` constant when adding a new default action so existing actors pick it up. `runDefaultAction(actor, item, opts)` is the dispatcher the sheet, the hotbar (`rules/hotbar.js`) and the combat menu (`macro/menu.js`, via `game.rpg.defaultActions`) call before falling through to the normal spell workflow — check `defaultActionKey(item)` there when adding a new baseline action rather than special-casing item names. The menu was the one caller that skipped it and went straight to `declareSpell`, which for these items means declaring a spell carrying no damage, no range and no effect: clicking "Attaquer" in the combat macro did nothing recognizable. A new surface that lists an actor's spells must route through the dispatcher too — these items are markers, all of their behavior lives there.

`ACTION_EXCLUDED_TYPES` keeps the weapon-based actions (`attaquer`, `changerArme`) off **monsters**: a monster has no weapons in this system — its attacks are its own `spell` items, which is what `triggerOpportunityAttack` already assumes — so "Attaquer" only ever offered it a bare-handed 1d4 and cluttered its ability list. Exclusion alone does not undo anything on monsters that were granted the action before the rule existed, so `grantDefaultActions` also *deletes* any baseline item whose key is excluded for that actor type, and `VERSION` was bumped so the backfill re-visits every actor once. The deletion is keyed on `flags.rpg.defaultActionKey`, never on the name — a GM-written monster ability that happens to be called "Attaquer" must survive. The combat menu applies the matching UI rule: no "Mains nues" fallback for a monster, so the Armes section simply does not appear unless the GM really equipped a weapon on it.

### Giving an item to an actor goes through `rules/inventory.js`, never `createEmbeddedDocuments` directly

`addItemToActor(actor, itemOrData, {qty})` is the single entry point for "this actor now has this item": it stacks (`system.qte += n`) when the actor already owns a matching item, and creates a new embedded document otherwise. `STACKABLE_TYPES` is **`loot` + `consumable`** — `weapon`/`armor`/`relic` each carry their own `equipe`/`emplacement` state (stacking them would make it impossible to wear one and keep another in the bag), and `spell`/`recipe`/`quest` aren't merchandise at all (a quest additionally carries its own progression). Matching is by **type + (case-insensitive name OR same compendium source)** — the OR is intentional: a renamed copy is still the same object, and two same-named objects from different packs are the same thing to a player looking at their bag. An exemplar the GM explicitly un-synced (`flags.rpg.linkSync === false`, the "🔗 Synchro" checkbox from `item-link.js`) is excluded in both directions — that flag already means "this one is unique", so it must not silently absorb or be absorbed by ordinary copies.

**`consumable` was excluded until a monster's loot table made the cost obvious, and the fix was a second condition, not a second exception.** The original reasoning — each copy carries its own `system.utilisations`, and a half-drunk potion is not a fresh one — is correct, but it argues for refusing to merge copies *in different states*, not for refusing to merge at all: ten identical unopened rations occupied ten inventory lines. `STACK_STATE_FIELDS` names, per type, the per-copy state fields that must be **equal** on top of the fingerprint (`consumable: ["utilisations"]`), checked by `stackCompatible()` inside `findStackTarget`. A partly-used flask still gets its own line; identical fresh ones merge. Adding a stackable type that carries per-copy state means adding its fields there — merging without it silently overwrites one copy's counter with the other's. Note nothing in the codebase currently *decrements* `utilisations` (it is a hand-edited GM counter, displayed only), so a future "consommer" action must decrement `system.qte` — removing one unit from the pile — rather than `utilisations`, or it would silently consume the whole stack at once.

Every path that hands an item to an actor was routed through it: drag-and-drop onto a sheet (`sheets/drop-helper.js`), the "📤 Envoyer" button (`sheets/send-item-dialog.js`), quest rewards (`rules/quest-resolve.js`), forge results (`rules/forge.js`), and the "Distribuer un Objet" macro (`macro/item-distribute.js`). Adding a new one and calling `actor.createEmbeddedDocuments("Item", …)` directly is the way to reintroduce the duplicate-line bug for that path only — which is exactly how it was reported. Two deliberate non-users: `character-sheet-v2.js`'s `_createItem` (the "+ Objet" button creates a *blank* item — stacking would merge every fresh "Nouvel objet" into one line) and `rules/default-actions.js` (baseline action items, not inventory). Macros can't `import`, so the module is also exposed as `game.rpg.inventory` (see the `game.rpg.*` bridge above); `item-distribute.js` reads `isStackableType` from there to decide whether a target that already owns the item stays selectable (stackable: yes, +1 to the pile) or stays greyed out (everything else).

### A recipe's ingredients are drag-and-dropped, and matched by the same fingerprint as everything else

`system.ingredients[]` entries used to be `{name, qty}` and were matched against the bag by **name only**. They are now `{name, qty, uuid, source, img, type}`, filled by dropping an Item anywhere on the recipe sheet (`setupItemRefDrop`, the same helper the quest sheet uses for rewards) — dropping an item already listed bumps its `qty` instead of opening a second row. The **Résultat** card is its own drop zone: its listener calls `stopPropagation()` so the sheet-wide handler doesn't *also* add the object as an ingredient (identical to the quest sheet's Récit-vs-rewards split).

- **`ingredientMatchesItem(item, ing)` in `rules/forge.js` is the single matcher**, used by `getInventoryQty`/`checkIngredients` *and* `consumeIngredients` — they must not diverge, or an ingredient recognized as available would never actually be removed from the bag. It reuses the codebase-wide fingerprint (same compendium source **OR** same lowercased name, `compendiumSourceOf` now exported from `inventory.js` rather than re-copied), so a renamed copy still counts and a recipe written before this change (name only) keeps working unchanged — only the second branch fires for it.
- **`ing.type` is what widens the search pool, and it is recorded at drop time.** Without it the pool is `loot`/`consumable`, the historical behavior. A GM dropping a weapon as a component (reforging a sword) would otherwise get an ingredient that can never be satisfied, silently, forever — the recipe would just become uncraftable with no message.
- **The fingerprint is captured on drop, never resolved at check time.** `checkIngredients` is called synchronously from `macro/forge.js`'s row builder; resolving a UUID there would need `await`. `dropSourceOf()` (recipe sheet) stores the compendium source — or the pack UUID when the dropped item *is* the compendium entry — so matching stays sync. A world item yields an empty `source`, and its name remains the only handle, exactly as before.
- **`uuid`/`source`/`img`/`type` travel through `<input type="hidden">` in the template.** The sheet is `submitOnChange: true` and `_onFormSubmitV2` rewrites the **entire** array from form data, so any field with no input would be wiped — typing one character in the quantity box next to a dropped ingredient would erase its reference. Adding a new per-ingredient field means adding its hidden input too.

### Reliques are a real Item type, sharing the armor sheet

`relic` is a full Item type (`template.json` + `system.json` `documentTypes` + `TYPES.Item.relic` in `lang/fr.json`), built from the same `baseItem`/`equipBonus`/`details` templates as `armor` — same bonuses, same `system.resistances`/`system.amplifications`, same equip-to-apply rule. It reuses `RPGArmorSheetV2` and `templates/item/armor-sheet.hbs` outright (registered for `["armor", "relic"]`), which branch on `ctx.isRelic` for the two things that actually differ: the header label, and the emplacement `<select>` being replaced by fixed text. Duplicating 250 lines of sheet for that would have let the two halves diverge the first time the bonus grid changes.

The `artefact` equip slot pre-existed the type — `SLOT_DEFS` in `character-sheet-v2.js` already listed it, but the options filter only ever offered `type === "armor"` items whose `emplacement` matched, and no armor could be set to `artefact`, so the slot was permanently empty and unusable. It is now `kind: "relic"` and lists **every** relic the actor owns without filtering on `system.emplacement`, because a relic's slot is imposed by its type, not chosen: `slotOfItem(item)` returns `RELIC_SLOT` (`"artefact"`) for any relic regardless of what its own field says. That matters because a relic imported/created with an empty `emplacement` would otherwise equip successfully while appearing in no slot at all — the classic "I equip it and nothing happens". The field is still written (`_toggleEquipItem`, `_onEquipSlotChange`, the sheet's submit handler) so the data self-heals on first touch. The technical key stays `artefact` while the user-visible label is "Relique" (`SLOT_LABELS`, now the single source for both the slot headers and the "Porté"/"Dans le sac" lines, which used to print raw keys).

Anything that enumerates worn equipment must list all three types — `weapon`, `armor`, **and** `relic`: `sumBonuses` in `documents/actor.js`, `isBonusActive` in `bonus-manager.js`, `getGearResistances` in `rules/resistances.js`, `getGearAmplifications` in `rules/amplification.js`, `CODEX_TYPES` in `rules/codex.js`, `SYNC_FIELDS` in `rules/item-link.js`, and the `estEquip`/`allEquipItems`/`_findEquippedForSlot` trio in `character-sheet-v2.js`. Missing one is silent: the relic equips fine and simply grants nothing. Monsters remain excluded from equipment bonuses entirely (`!isMonster` in `sumBonuses`), relics included.

### Linked-item sync reaches every holder, not just player characters

`rules/item-link.js` propagates *definition* fields (a per-type whitelist, `SYNC_FIELDS`) from any edited item to every other copy that shares its fingerprint (compendium source, else type+lowercased name — same heuristic as `codex.js` and `inventory.js`). It is on by default, per-copy opt-out via the "🔗 Synchro" checkbox (`flags.rpg.linkSync === false`), and driven by one central `updateItem` hook so no write path can miss it. Three things it must keep doing:

- **It enumerates every actor, plus the unlinked tokens of the loaded scene.** The original loop skipped anything that wasn't `actor.type === "character"`, which read from the outside as "sync works for equipment but not for spells or objects": weapons and armor are worn by PJ/PNJ (both `character`), while spells and loot mostly live on **monsters**, which the loop never looked at. Unlinked tokens keep their own item copies in the token delta, outside `game.actors`, so they're swept too — but only for the scene currently loaded, since Foundry doesn't have the others in memory (a monster on an unopened scene stays stale until it's re-placed from its prototype).
- **`name` and `img` propagate, and a rename is matched on the fingerprint captured in `preUpdateItem`.** By the time `updateItem` fires the document already carries the new name, so matching on the current fingerprint would find nobody. Worse, *not* propagating a rename doesn't just leave stale labels — it silently evicts the renamed copy from the group forever, since the fallback fingerprint is the name itself.
- **The whitelist is per-field, not per-object, wherever an object mixes definition and runtime state.** `system.cooldown.max` (the GM's "Recharge" field) syncs while `system.cooldown.restant` must not; `system.aura.{target,key,range,dotFlat,cleanseDC}` sync while `system.aura.active`/`enabled` must not — those last two are in `init.js`'s player-write whitelist precisely because players toggle them. Excluding a whole branch because part of it is instance state (which is what `system.aura` used to do) silently drops real definition fields.

### Codex: compendium visibility is possession-gated

`rules/codex.js` filters `renderCompendium` for non-GMs so item-type compendiums only show entries a player's character has ever had (`flags.rpg.codex` on the actor, populated by `createItem`, matched against compendium entries by source UUID / id / lowercased name — never purged, since "has had" persists after an item is sold or consumed). Non-item compendiums (journal/rules, roll tables) are never filtered. Monster actor sheets are separately gated: GM must set `system.pvReveal` (`none`/`pct`/`exact`) to reveal anything beyond illustration+description, and monsters need at least `LIMITED` ownership for a player to open the sheet at all (`openMonsterToPlayers`, run once per monster the first time it's touched by `grantDefaultActions`/backfill — never overrides a GM-set ownership level).

A compendium Item dragged onto an actor becomes an **independent embedded copy** — Foundry does not keep it linked to its compendium source. Renaming/editing the actor's copy never updates the compendium entry, and vice versa; this is stock Foundry behavior, not something to "fix" in this codebase.

### États actifs are matched by label on add, not by id

`system.etatsActifs` entries (`_stateUpsert` in `character-sheet-v2.js`/`monster-sheet-v2.js`) don't carry the effect catalog's stable `key` (`rules/effect-library.js`) — only a free-text `label`. `_stateAdd()` always starts from a fresh `foundry.utils.randomID()`, so re-applying an effect a target already has (e.g. clicking "Ajouter un état" and picking "Brûlure" again) would previously never match the existing entry and just stacked a duplicate with its own independent countdown. `_stateUpsert` now falls back to matching an existing entry by case-insensitive `label` whenever the id doesn't match anything (a genuine new add), and replaces it in place instead of stacking. Note this is the *manual GM dialog* path — `applyEffect()` in `rules/status-effects.js` (spell-driven effect application) already stacked/replaced correctly via `effectDef.key` and `stacking: "replace"`.

### Theming is global and mandatory per-window

`styles/theme.css` defines the design tokens (`--ink`, `--brass`, `--ember`, `--el-*`, etc.) for three user-selectable themes (`sombre`/`clair`/`contraste`, world/client setting `rpg.uiTheme`). Every sheet must call `applyUiTheme(root)` (`sheets/sheet-helpers.js`) from its own `_onRender`, and `applyGlobalTheme()` (called once from `init.js`'s `ready` hook) stamps the theme class on `<body>` so non-sheet windows (macro dialogs, DialogV2 prompts) inherit it too. A new sheet or macro dialog that skips this will render in Foundry's default (unthemed) look regardless of the user's choice.

The class each theme actually stamps is **`rpg-theme-clair`/`rpg-theme-contraste`/`rpg-theme-sombre`** (the `rpg-` prefix, per `THEME_CLASSES` in `sheet-helpers.js`) — a selector written as `.theme-clair` instead of `.rpg-theme-clair` will silently never match, in any theme, forever (this bit `<select> option`/`<optgroup>` styling in `item-sheet.css` for a long time: the light/contrast override was dead code, and only `.rpg-sheet` was targeted at all, so any window with only `.rpg-window` — e.g. `applyGlobalTheme`'s macro-dialog theming — got zero option styling and fell back to the OS's unthemed native dropdown list). `<select>` option/optgroup colors are centralized once in `theme.css`, scoped to `.rpg-sheet`, `.rpg-window`, and `.rpg-spell-menu` together, reusing `--ink-2`/`--ink-text`/`--brass` rather than hardcoded per-theme hex — add a new window class to that block too if it needs themed dropdowns.

`themeIfOurs()` in `init.js` (the `renderApplication`/`renderApplicationV2`/`renderDialog`/`renderDialogV2` handler that calls `themeWindow()`) recognizes 100%-native-but-integral-to-the-game windows by document TYPE, never by content sniffing — RollTable and JournalEntry/Page were the first two (see below); Macro sheets (`isMacroSheet`, `documentName === "Macro"`) and popped-out world document directories (`isWorldDirectory`, any sidebar tab — Objets, Acteurs, Scènes… — detached into its own floating window) were added later, same reasoning each time: reported as staying fully dark/native regardless of the chosen theme, because nothing in their DOM carries `.rpg-sheet`/`.rpg-window`/etc. `isWorldDirectory` checks `app.collection.documentName` being set while `packId` (the same pack-metadata check `isOwnPack` uses) is *not* — that's what distinguishes a WORLD collection browser (`game.items`, ours to theme) from a compendium browser for a pack that isn't ours (already excluded, and must stay excluded — theming another module's or core's compendium browser would be exactly the over-reach this whole detect-by-type-not-content approach exists to avoid). The *docked* sidebar (`#sidebar`/`#chat`/`#hotbar`) is still never touched, on purpose — that exclusion is a separate, still-valid rule (avoids repainting the chat log) and only applies to the docked instance; a popped-out directory is a distinct floating `Application` no longer nested under `#sidebar`, so it reaches the `isWorldDirectory` check at all.

Marking a macro's edit window `.rpg-window` alone isn't enough to fix its "Script" type's CodeMirror editor, though — CodeMirror keeps its own internal theme (background + syntax colors, designed together for a dark `color-scheme`), which is a different mechanism from anything else `.rpg-window` touches. Once the window inherits `color-scheme: light` (from the Clair theme block), Foundry's `light-dark()`-based editor text recolors to light-mode (dark) tones while the editor's own background — not driven by the same mechanism — stays dark: dark-on-dark, nearly invisible, and specific to Clair (Sombre/Contraste already want a dark color-scheme, so they never expose the mismatch). Fix is a targeted `color-scheme: dark !important` scoped to `.cm-editor` inside `.rpg-window`/`.rpg-sheet` (`theme.css`) — pins the editor's own internal fond/texte computation back to a self-consistent pairing regardless of the theme chosen around it, without repainting the syntax-highlighted text ourselves (which would just trade one contrast bug for a flatter, less readable editor). This is the same `light-dark()`/`color-scheme` mechanism a previous fix already scoped away from `<body>` — that fix was necessary but not sufficient, since it only stopped the leak to windows we *don't* mark; it did nothing for windows we deliberately *do* mark, which still inherit `color-scheme` from their own `.rpg-theme-*` class by design.

**Pinning `color-scheme: dark` on `.cm-editor` fixed the *background*/CodeMirror-computed colors, but not a color WE impose from outside — a GM still reported dark-on-dark text in Clair after that fix shipped.** `body.rpg-theme-clair .rpg-window .window-content { color: var(--ink-text) !important; }` (the journal reading-pane fix, same file) sets `--ink-text` to `#2b2418` in Clair — dark ink meant for a light page. `color` is inherited, and even with `!important` on the ancestor, any descendant with its *own* color rule still wins over inheritance — but CodeMirror's unstyled/default text (whitespace, punctuation not covered by a specific syntax-token class) has no rule of its own, so it just inherits, and the *nearest* ancestor's value wins no matter how many levels up it sits. `.cm-editor` is a descendant of that same `.window-content`, so its default text inherits `#2b2418` — landing on top of a background that's still correctly dark (background isn't inherited, so the earlier `color-scheme` fix was never wrong, just incomplete), reproducing the exact "quasi invisible" symptom the `color-scheme` fix already describes, just via a completely different, later, unrelated rule that never accounted for CodeMirror living inside `.window-content` too. Only syntax-highlighted tokens (which set their own explicit color) survived; everything else vanished. Fixed the same way as the earlier `color-scheme` pin: give `.cm-editor` itself an `!important` default `color` — closer in the DOM than `.window-content`, so anything without its own color rule inherits *this* instead, while tokens with their own rule are untouched either way. Hardcoded, not `var(--ink-text)`: `.cm-editor` is *always* a dark island regardless of the chosen theme, so it can't read a theme-dependent variable — used `#ece4d3`, this system's own Sombre `--ink-text`, so the editor reads as consistently "Sombre-flavored" regardless of which surface it's actually nested under.

### Every sheet's window id must be unique per document

ApplicationV2 uses `this.id` twice: as the key it registers under in `foundry.applications.instances`, and as the `id` attribute of the window element it inserts — and `_insertElement()` *replaces* whatever element already carries that id. A static `id` in `DEFAULT_OPTIONS` therefore means the second sheet of that type rips the first one's window out of the DOM, while the first instance still believes it is rendered (`document.sheet` keeps it cached, its state stays RENDERED). Reopening it then re-renders its parts into a detached element: nothing appears, and nothing is logged. Reported as "after opening item sheets a few times, they refuse to open, with no console error" — all six item sheets shared one id apiece (`rpg-weapon-sheet-v2`, `rpg-spell-sheet-v2`, …).

**Overriding `get id()` does not fix this** — that was the first attempt, and the GM reported the bug unchanged. ApplicationV2 freezes its id at construction into a private field, read from `options.id`, and it is *that* field which becomes the element's `id` attribute and the `foundry.applications.instances` key; a subclass getter never enters the picture. The id has to be made unique on the OPTION, before the constructor reads it: every sheet now overrides `_initializeApplicationOptions()` and routes it through `uniqueSheetOptions(appOptions, rawOptions, baseId)` (`sheets/sheet-helpers.js`), which sets both `options.uniqueId` and `options.id` to `<baseId>-<uuid>`.

**The UUID, not `document.id`** — that part matters for actors and embedded items alike: two unlinked tokens of the same monster share their actor's id, and each token's copy of an item shares the prototype item's id, so an id-based key still collided exactly where the GM is most likely to open two sheets side by side. The character and monster sheets had id-based getters (added for this same reason, and equally ineffective) and were converted at the same time.

A last-resort net sits in `init.js`'s `renderApplicationV2` handler: a window element of ours that renders while detached from the document (`!root.isConnected`) is re-appended to `<body>`, with a console warning. Rendering into a detached element is the exact shape of this whole family of "the sheet refuses to open, nothing in the console, only F5 helps" reports — including the still-open journal one documented in that same handler — so healing it is worth more than the theory behind any single cause.

### Scroll position is restored by one shared helper, in every sheet's `_onRender`

Nearly every action on a sheet re-renders it whole (`submitOnChange: true`, plus the explicit `this.render({ force: true })` after equipping an item, checking a box, adding a row…). The content element is replaced, the browser clamps the scroll position of whatever was scrolling, and the window snaps back to the top — reported repeatedly, most recently as "équiper un équipement fait remonter la fenêtre" from the character sheet's Équipement tab. `restoreScrollPositions(root)` (`sheets/sheet-helpers.js`) is the single fix, and **every** sheet must call it from `_onRender` — character, monster, the six item sheets, and both RegionBehaviorConfig subclasses do. Three things about it are load-bearing:

- **It watches `.window-content` as well as `.sheet-body`.** Foundry's own `PARTS[…].scrollable` option (declared on the character and quest sheets) can only name a selector *inside* the part element, and on these sheets the element that actually carries the scrollbar is `.window-content` — a frame element, outside the part — because core's `.application .window-content { overflow: hidden auto }` outranks our `.rpg-sheet-window { overflow: hidden }` on specificity. That's why `scrollable` looked declared-and-working while doing nothing, and why the spell sheet's own `_snapshotView` (which read `.sheet-body` first, via `??`, so it always captured a `0`) never restored anything either. Both selectors are watched, and only an element that actually emitted a `scroll` event is ever memorized, so listing a non-scrolling one costs nothing.
- **The memory is a `WeakMap` keyed by `app.element`, not a field on the Application.** Foundry caches the sheet instance (`document.sheet`) after a close but destroys and rebuilds its element, so keying on the DOM gives a reopened sheet a fresh start at the top while a re-render — which keeps the same frame — keeps its position. The monster sheet's earlier hand-rolled version stored `this._scrollTop` and so restored across reopens; that was the one intentional behavior change when it was folded into the shared helper.
- **A scroll event reporting 0 on a container with nothing left to scroll is ignored.** Writing `scrollTop` fires `scroll`, and so does the browser's own clamp when the freshly-replaced content is momentarily too short — recording either would erase the very position being restored. Restoration is bracketed by a `restoring` flag (cleared two frames later, since the second `requestAnimationFrame` pass is what catches content whose final height arrives late: images, fonts, resized textareas), and the `scrollHeight - clientHeight <= 0` guard covers a clamp that lands outside that window. Verified against a fake DOM that clamps and dispatches `scroll` *synchronously* — stricter than a real browser, where those events are deferred to the next rendering update — over four scenarios: first render, re-render after scrolling, close/reopen, and a deliberate scroll back to top (which must be remembered, not undone).

The quest sheet is the one deliberate partial user: it keeps its own `_preRender`/`_onRender` handling of `.quest-page-content` (excluded from the helper's selector list) because it must *not* restore that pane when an action changes page — "+ Étape" jumps to the new step on purpose.

### Attack range: `allonge` ∪ `range.max`, measured edge-to-edge in meters

`rules/weapon-range.js` is the single definition of "can this weapon reach that target", used by the combat menu's `Attaquer` button, the baseline `Attaquer` action (`runDefaultAction`), and — through the shared `tokenFootprintMeters` — the rings drawn on the canvas. Two prior sources of disagreement it exists to remove:

- **A weapon has two range fields and they mean different things.** `system.allonge` is melee reach (default 1 m; it drives threat zones, opportunity attacks and the ⚔ ring), `system.range.max` is throw/shot range (the weapon sheet literally tells the GM to copy the allonge into it for a pure melee weapon). `macro/menu.js` gated on `range.max` alone, so a sword whose `range.max` was left at 0.5 — or at 0, which nothing forbids — could not attack an adjacent target while the threat ring on the map showed that same target as reachable. Effective range is now `max(allonge, range.max)`, which leaves a bow's 30 m intact and lets a mis-filled melee weapon fall back on its reach.
- **`game.rpg.measureDistance` is Manhattan distance in GRID SQUARES**, despite being compared against ranges expressed in meters (the menu's own variable was named `distCases` and printed with an "m" suffix). It only coincides on a 1 m grid, and never on a diagonal, which it counts as 2. Range checks use Euclidean meters minus both tokens' footprints — the same measurement the canvas rings use, so the button and the circle can no longer contradict each other. `measureDistance` stays exported for anything that genuinely counts squares.

The baseline `Attaquer` action checked no range at all before this (only the menu's weapon rows did), so the sheet and the hotbar could attack from anywhere on the map.

### Movement is metric, not grid-square

Distances are computed in meters via weighted-diagonal movement cost (`rules/movement-tracker.js`, `rules/distance.js`), not raw grid squares — terrain difficulty (`rules/region-behaviors.js`, V13 drawn Regions) and movement-type immunities (`rules/movement-types.js`) both scale this cost. Because cost isn't linear when terrain varies along a path, clamping a drag to "however far is left" requires a binary search over `calculateMovementCost` (`rules/drag-limit.js`) rather than vector scaling. The speed limit is enforced twice: at drag-time (visual clamp, `drag-limit.js`) and at commit-time (`onPreUpdateToken` in `movement-tracker.js`, which clamps rather than outright rejects an over-budget move so V13's non-`return false`-honoring token update doesn't leave the player confused).

**`CONFIG.Token.rulerClass` must be swapped in the `init` hook, not `ready`.** `movement-ruler.js`'s `installRPGTokenRuler()` subclasses `CONFIG.Token.rulerClass` to make the live drag-measurement label show the real RP cost (`calculateMovementCost` — diagonals + terrain) instead of Foundry's raw grid distance. It used to be installed from `ready`, alongside `installRangeOverlay()`/`installDragLimit()` — but unlike those two (one only registers event hooks, the other monkey-patches a shared `Token.prototype` method, both timing-independent), `rulerClass` is a class *reference* Foundry reads to construct each token's ruler at canvas/token draw time, which for the initially-loaded scene has already happened by the time `ready` fires. Reported symptom: the drag label showed a plain, native-looking `🚶 X m` that never changed no matter what terrain was crossed — our subclass's `_getWaypointLabelContext` override was simply never in place for tokens already on the canvas at startup. Moved to `init` (before any canvas/token construction), alongside the other early setup — `installRangeOverlay()`/`installDragLimit()` correctly stayed in `ready`, since neither has this class-reference timing problem.

**`calculateMovementCost` must sample terrain along the WHOLE segment, not just its midpoint.** A prior fix to the drag-ruler timing (above) asserted the cost engine itself was "sound... terrain lookup and the speedMult-based cost inflation are both sound" — that assessment was wrong, just not exercised by the case it was checked against. `region-behaviors.js`'s per-segment loop looked up terrain at exactly one point, `((from.x+to.x)/2, (from.y+to.y)/2)` — the segment's midpoint — and applied whatever multiplier it found (or didn't find) to the segment's *entire* raw distance. Both `drag-limit.js` (the visual clamp deciding how far a drag is even allowed to go) and `movement-ruler.js` (the live cost label) always call this with a single `[dragOrigin, currentMousePoint]` pair — one long segment for the whole gesture, not one per grid cell — so the midpoint is frequently nowhere near the actual terrain boundary. Concretely: dragging 6m where a "Terrain difficile" (×0.5) region only covers the last 2m has its midpoint at the 3m mark, still on normal ground — the region is never detected, the drag is never slowed, and the player can walk straight through difficult terrain at full speed the moment the patch doesn't happen to straddle dead-center of their whole move. This matches the reported symptom exactly (terrain silently doing nothing) and is the general case, not an edge case — a player dragging *toward* or *into* a terrain patch (rather than dragging with the patch conveniently centered on their path) hits it on essentially every drag. Fixed by sub-dividing each segment into ~half-grid-cell steps (`stepCount`, capped at 64) and summing each step's own terrain-sampled cost (`_terrainMultAt`) instead of extrapolating one sample over the whole distance; contiguous same-terrain steps are merged back into one `segments` entry so the chat summary still reads as a single clean line ("3m en Terrain difficile") rather than dozens of tiny ones. Verified numerically (not in a live Foundry session): the same 6m/2m-of-terrain drag went from `cost=6, terrainsCrossed=[]` (bug — terrain invisible) to `cost=8, terrainsCrossed=['terrainDifficile']` (4m normal + 2m at double cost) after the fix.

**`RegionDocument#testPoint` takes an ELEVATED point `{x, y, elevation}`, and omitting `elevation` doesn't just make the check imprecise — it makes it fail unconditionally, for every region, always.** The subdivision fix above was real and necessary, but a GM still reported terrain difficulty having *zero* effect after it shipped — for a drag sitting entirely inside one large "Terrain difficile" region, a case the subdivision fix doesn't even touch (every sample lands in the same region regardless of granularity). The actual, deeper bug: every `_pointInRegion` in this codebase (`region-behaviors.js` *and* its near-identical twin in `zone-effects.js`) called `region.document.testPoint({ x, y })` — no `elevation` key at all. Foundry compares the point's elevation against the region's elevation bounds (`-Infinity`/`Infinity` by default, meaning *no* restriction), but in JS, `undefined >= -Infinity` evaluates to `false` (a numeric comparison against `undefined` coerces to `NaN`, and any comparison with `NaN` is `false`) — so a point with no `elevation` key fails that bounds check even against a region with *no elevation restriction configured at all*. Net effect verified against a `testPoint` mock that actually enforces this comparison (a permissive mock that ignores elevation, like an earlier debugging session's, would never have caught this): `getTerrainAt`/`getZoneEffectsAt` returned **zero matches for every region, unconditionally** — not a sampling-granularity problem, but total, universal failure, exactly matching a standing "terrain difficile still does nothing at all" report regardless of drag geometry. Fixed by threading a real `elevation` value end to end: `calculateMovementCost(waypoints, actor, elevation)` → `_terrainMultAt` → `getTerrainAt(x, y, elevation)` → `_pointInRegion(region, x, y, elevation)` → `testPoint({x, y, elevation})`, same chain in `zone-effects.js` for `getZoneEffectsAt`/`triggerZoneEffectsForToken`. Every caller that has a real token handy now passes its actual `tokenDoc.elevation` (`movement-tracker.js`'s `onPreUpdateToken`/`_processMove`, `drag-limit.js`'s `clampDestination`, `movement-ruler.js`'s `_getWaypointLabelContext`); everything else defaults the parameter to `0`, matching a normal un-elevated token and Foundry's own `TokenDocument#elevation` default — never leave it as `undefined`/omitted again, since that specific value is the one guaranteed to break the comparison. `_processMove`'s snapshot now also carries `elevation` so `action-confirm.js` can forward the mover's real elevation into `triggerZoneEffectsForToken` at GM-validation time instead of implicitly defaulting to 0 for a token that wasn't actually on the ground.

**A reach/threat ring's radius must match the number in its own label.** `range-overlay.js`'s `tokenFootprintMeters()` adds half a token's own width to every drawn ring (`showMovementLimit`, `drawRanges`, `updateDragThreatIndicator`) so a large creature's threat zone doesn't fall entirely under its own base — but it used to add the token's *entire* half-width unconditionally, even for a normal 1×1 token. On a 1-meter grid, adjacent 1×1 tokens already sit exactly 1m apart center-to-center, so a weapon's reach measured from the center already lands exactly on an adjacent square's edge — nothing needs adding. The old code still added a full 0.5m anyway, so a ring labeled "1,5 m" (the raw weapon-sheet value, deliberately kept unscaled per an earlier fix so the number on the map matches the number on the sheet) was actually drawn at 2m — reported directly by a confused player. Fixed to return only the *excess* beyond a normal half-square (`max(0, halfWidth − gridDistance/2)`): zero for any 1×1 token, still positive (and still necessary) for anything bigger.

**A single mouse-drag fires `preUpdateToken`/`updateToken` several times in V13**, not once at drop — the token's position is live-updated while you drag, not just on release. Code that reacts to these hooks (`movement-tracker.js`'s clamp-and-correct logic) must not treat itself as a one-shot: don't unconditionally clear a pending correction (`_pendingRevert`) at the top of `preUpdateToken`, since a later live-drag tick can otherwise wipe out an earlier tick's not-yet-applied correction before it lands, and the token settles somewhere wrong (often back at the drag's start). Only overwrite/clear that kind of per-token pending state when you're about to replace it with a fresh value, and coalesce any user-facing toast the clamp fires (`_notifyOnce`) since the same wall gets hit repeatedly within one gesture.

**Visual range/threat overlays must track the active combatant, not local selection.** `rules/range-overlay.js`'s movement-budget circle and melee-reach ring were originally driven by the `controlToken` hook, so they only ever rendered on whichever client had that specific token selected — which meant the GM, who almost never controls a player's token, never saw them during that player's turn. They're now driven by `game.combat.combatant` (refreshed on `updateToken`/`updateCombat`/`canvasReady`), so every client renders them for whoever's turn it is, with no selection or hover needed. Anything meant to be visible to the GM during someone else's turn should follow this pattern, not `controlToken`.

### Quest items: the reward is GM-only, steps get a player-visible narrative field

`sheets/item-quest-sheet-v2.js` + `templates/item/item-quest-sheet.hbs`: each `system.etapes[]` entry has three player-relevant fields — `label` (title), `description` (the actual narrative text for the step, player-visible while it's the current one — this is where the GM writes what happens, distinct from the checkbox `objectifs[]` list and from `notesMJ`), and `notesMJ` (GM-only, stripped out entirely for non-GM viewers, never just hidden in CSS). `system.recompense` (XP + reward items) is hidden from players on **two** independent layers — the template section is gated behind `{{#if isGM}}`, and `_prepareContext` also zeroes it out (`{ xp: 0, items: [] }`) in the context built for non-GM viewers — because the template gate alone still leaves the real values sitting in the rendered document data. A step only becomes visible to players once the GM advances `system.etapeActuelle` via the "Étape suivante" button (`canEdit`-gated, GM-only); everything past that index is filtered out of the player-facing context, not just visually hidden.

### A player opening someone else's character sheet gets a PNJ card, not the sheet

There is no `npc` Actor type — NPCs are ordinary `character` actors (that's what an `@UUID[Actor.…]` link in a quest/journal opens). `RPGCharacterSheetV2._isNpcView()` (`static isNpcViewFor(doc)`) decides, per viewer: a non-GM who is **not** an owner gets the "carte PNJ" branch at the top of `templates/actor/character-sheet.hbs` (`{{#if flags.npcView}}`) — large illustration (click = lightbox via the now-exported `openImageLightbox` in `sheet-helpers.js`), name, enriched `system.description`, and the active `etatsActifs` — instead of the full sheet. Same two-layer rule as the quest reward: the template branch is only half of it, `_prepareNpcContext()` also rebuilds the render context from scratch (`ctx.system = {}`, `delete ctx.source`) so no stat ever reaches the rendered data. `system.pnjView` (`auto`/`always`/`never`, GM-only select in the new 🎭 PNJ / RP tab) overrides the default heuristic, which is `!doc.hasPlayerOwner` — true of every NPC, false of every player character, so a party still sees each other's full sheets and the GM never has to tick a box per NPC. GM-only staging fields live under `system.mj` (`caractere`/`dialogues`/`secrets`) and are rendered **only** inside `{{#if flags.isGM}}`; `system.description` is the one field of that tab players read. The state summaries shown on the card come from `decorateStates()`, extracted from `_prepareContext` so both views describe an effect identically.

The monster sheet reaches the same shape by a different, older route (`canSeeStats`/`pvReveal`, already GM-gated) — for players its illustration now renders big in the body (`.rpg-npc-card`, shared CSS) rather than as a 64px header thumbnail, plus a read-only list of its active states.

**That same PJ/PNJ split is what every distribution list sorts by, and it lives in `rules/actor-roles.js`** — `isNpcActor(actor)` (pnjView override, else `!hasPlayerOwner`) is now the single definition, with `isNpcViewFor` delegating to it, so the sheet's notion of "this is a PNJ" and the target lists' notion can't drift apart. Reported as: the "📤 Envoyer" popup and a quest's "Qui voit cette quête ?" listed every `character` actor, so world NPCs sat inline among the player characters with nothing distinguishing them (both are the same document type — folder names like "PJ"/"PNJ" in the sidebar are pure GM organization the code never reads, and must not be read: renaming a folder would silently reclassify everyone in it). Both surfaces now render PJ first and NPCs in a separate collapsed section (`splitCharacters()`), each group with its own "tout cocher"; `macro/item-distribute.js` (via `game.rpg.actorRoles`, macros can't import) groups PJ / PNJ / Monstres with per-group headers, and `macro/recipe-distribute.js` sorts PJ first and tags NPCs inline.

NPCs are deliberately **grouped, never dropped**, from those lists: a player character whose user account hasn't been assigned yet has no player owner, so `auto` classifies it with the NPCs — filtering them out entirely would make that character unreachable from the very windows the GM uses to hand it its starting gear, with no visible reason why. The durable fix for such a case is the sheet's own 🎭 PNJ / RP select (`pnjView: "never"`), which the collapsed section points the GM to.

### Environmental triggers: pièges and zone spells share one region behavior

`rules/zone-effects.js` registers `zoneEffet`, a generic Foundry V13 RegionBehavior data model covering both hidden traps and visible spell zones (wall of thorns, poison cloud...): direct damage (dice formula + physique/magique, routed through `computeFinalDamage`/`applyFinalDamage` from `combat.js` for normal armor/résistance mitigation) and/or a status effect (via `applyZoneStateEffect`, a local wrapper around `applyResistances()` from `resistances.js`) on entry, plus a `speedMult` that folds into the existing terrain slowdown — `getTerrainAt` in `region-behaviors.js` now also scans `getZoneEffectsAt` and injects synthetic terrain-shaped entries into its result, so `calculateMovementCost` and the drag-time speed check in `movement-tracker.js` pick zones up for free, no separate code path. There's no true movement block, consistent with the "impassable" flag on `TERRAIN_TYPES` (documented but never enforced) — a zone can only be slowed to near-impassable (`speedMult` down to 0.1), never a hard refusal; don't add one without also revisiting the movement-tracker refusal path (`_refuseMove`).

**RegionBehavior subtype keys registered by the system itself are never prefixed with the system id** (`zoneEffet`, `terrainDifficile`, ... — not `rpg.zoneEffet`), same rule as Actor/Item (`Actors.registerSheet("rpg", ..., { types: ["character"] })` — the `types` array is unprefixed; the `"rpg"` scope argument is unrelated to the type string). Only a *module* declaring its own RegionBehavior type would prefix with its module id. Foundry assigns the raw `system.json` `documentTypes.RegionBehavior` key to a behavior created from the native "Add Behavior" menu — a `"rpg."`-prefixed key registered in `CONFIG.RegionBehavior.dataModels`/`typeLabels`/`typeIcons` never matches that document, so its `system` never gets wrapped in a real DataModel and the core `RegionBehaviorConfig` sheet throws `Cannot read properties of undefined (reading 'schema')` the moment it tries to render — permanently, for every behavior of that type. Also: `foundry.applications.sheets.RegionBehaviorConfig.registerConfig(type, SheetClass)` is not a real Foundry API (a prior session invented it and silently swallowed the resulting `TypeError` in a bare `try/catch`, so it looked like registration succeeded) — the real mechanism for attaching a custom sheet class to a RegionBehavior subtype is `foundry.applications.apps.DocumentSheetConfig.registerSheet(getDocumentClass("RegionBehavior"), "rpg", SheetClass, { types: [...], makeDefault: true })`, the same underlying call `Actors.registerSheet`/`Items.registerSheet` wrap for Actor/Item.

Triggering is wired into `action-confirm.js`'s move-confirm branch (`triggerZoneEffectsForToken`), **not** `movement-tracker.js`'s `preUpdateToken`/`onUpdateToken` — it only fires once the GM clicks ✅ on the pending move chat message, keeping it inside the declare → GM-validate → resolve flow instead of firing at mere declaration. `hidden: true` (the default) only controls whether the Region graphic is visible on the GM's own canvas; it doesn't gate the trigger's chat message, which is posted openly once the trap has actually gone off — the player who tripped it is expected to learn what it was at that point. Detecting a trap *before* stepping on it is a separate path (`declareZonePerceptionCheck` / `revealZoneToActor`, driven from the "Détecter un piège" macro — select the searching token + the region, see below for what "select the region" actually means): success only whispers a description to the GM and the actor's owners, it does **not** make the Region itself visible to that player, since Foundry Regions have no supported per-player visibility toggle — showing it on the map afterward is a manual GM step (a Drawing, a Note, narrating it).

**Zone/piège triggering never fired for movement made outside of combat — reported as "a player standing on a trap does nothing."** `triggerZoneEffectsForToken` is called from exactly one place, `action-confirm.js`'s move-confirm branch, itself only reachable once `movement-tracker.js`'s `onUpdateToken` has built a pending-move chat message for the GM to validate — and that whole pipeline (debounce → budget reservation → chat message → GM confirm) is gated behind `isCombatEngaged(game.combat)` (`combat.active && combat.round > 0`), a guard that exists for the *action-economy* tracking (nobody has a turn/movement budget outside combat). Since most pièges are actually encountered during ordinary dungeon exploration — not a structured turn-based combat — this meant traps were, in practice, entirely inert outside of combat: not flaky, not occasionally missed, just never wired to fire at all in that mode. Fixed by adding a second, minimal path in `onUpdateToken`: when `!isCombatEngaged(...)`, skip the whole budget/pending-message machinery (nothing to reserve, no chat approval needed) and instead debounce (same `DEBOUNCE_MS`, same reasoning — one V13 drag gesture fires `updateToken` several times) straight into `triggerZoneEffectsForToken` at the token's settled position, still only on the GM's own client (the function already no-ops for `!game.user.isGM`, matching the same permission shape the combat path relies on). In-combat behavior (fire only once the GM clicks ✅ Valider) is untouched — this only fills the gap where that pipeline never engaged in the first place.

**Zone/piège triggering was still missing in combat too, even after the out-of-combat fix above — the root cause was a coordinate mismatch, not a gating problem.** Every position fed to `triggerZoneEffectsForToken`/`getZoneEffectsAt` (drag-time clamp in `onPreUpdateToken`, the full-path terrain-cost sampling in `_processMove`, and my own out-of-combat scheduler) used `tokenDoc.x`/`tokenDoc.y` directly — the token's TOP-LEFT corner, the literal document field. Every OTHER position-based check in this codebase (`range-overlay.js`, `drag-limit.js`, `movement-ruler.js`, `gm-aura.js`, `aura-render.js`) instead uses the token's CENTER (`token.center`) — `drag-limit.js`'s own docstring even calls its drag-destination parameter "centre, non alignée", matching Foundry V13's `Token#_updateDragDestination` API, which hands you a center point, not a corner. For a region shape that doesn't happen to blanket the token's entire occupied grid cell — exactly the case in the reporting GM's screenshot, an irregular rectangle covering only part of the token's cell — testing the corner instead of the center can and did land outside the region while the token's visible body (drawn centered) clearly overlapped it. Fixed by adding `_tokenCenterAt(tokenDoc, x, y)` in `movement-tracker.js` (computes the center for a given, possibly hypothetical, top-left position — needed since the drag-time clamp tests a destination that hasn't been committed yet) and routing every terrain/zone sample point through it: the destination check in `onPreUpdateToken`, the waypoints passed to `calculateMovementCost` in `_processMove` (safe to shift uniformly — segment distances are invariant to a constant offset, only the terrain-sampling accuracy changes), and the point passed to `triggerZoneEffectsForToken`. The snapshot gained a separate `centerX`/`centerY` pair for the zone-trigger test point — `newX`/`newY` (still the true corner) must stay untouched since `undoMovement()` uses them to literally reposition the token via `tokenDoc.update({x, y})`. Also added `console.debug` breadcrumbs in `triggerZoneEffectsForToken` (zones found at the tested point, and why each candidate zone was skipped — onceOnly already consumed, immune via groundOnly, or target-disposition mismatch) so a future "nothing happens" report can be read straight out of the console (F12) instead of guessed at blind.

**A zone/piège can now target only allies or only hostiles** (`system.targetDisposition`, `zone-behavior.hbs`'s "Cible" select: Tout le monde / Alliés seulement / Hostiles seulement) — filters by the TOKEN DISPOSITION of whoever walks onto it (never the actor type — a hostile NPC is a "character" document just like a player, same reasoning as `areOpposedDisp()` in `movement-tracker.js`), checked in `triggerZoneEffectsForToken` via `_targetMatchesDisposition()`. `"tous"` (default) preserves the old unfiltered behavior for every zone configured before this field existed. Motivating case: a trap a player sets up should generally only hurt hostile creatures, not their own allies walking over it later.

**A Region/RegionBehavior cannot be hidden from the GM — Foundry's permission model has no such concept, and building a fake version of it would be actively misleading.** Asked whether a player could place a piège "invisible even to the GM" once the GM approves it: the GM role is omniscient by design over every document in a world (Scenes, Regions, Tokens, Actors) — there is no ACL that restricts a GM account's own visibility, unlike the player-facing `hidden`/ownership controls this system already builds on top of Foundry (chat-visibility.js's `.rpg-gm-only`/`.rpg-hp-secret`, monster `pvReveal`, etc., all of which only ever restrict what PLAYERS see, never what the GM sees). Concretely, a player also lacks Region/RegionBehavior *create* permission by default (that's a GM-only document type), so the actual document would have to be created by the GM's own client regardless of the workflow — same "declare → GM validates → resolves" shape already used for spells/attacks/moves (`action-confirm.js`) would work here too (player proposes params in a chat message, GM clicks a button that creates the Region+`zoneEffet` behavior), but the GM necessarily sees the exact parameters at the moment they approve it, since they're the one whose client executes the creation. Not implemented — surfaced as an open question for the user to confirm they still want the propose/approve workflow given that constraint, rather than building something that silently doesn't deliver on "hidden from the GM."

**A Region's shape is not clickable on the canvas — reported as "zones stop being configurable once set up," but this is stock Foundry, not a regression in this system.** Foundry does not hit-test a Region's drawn geometry the way it does Tokens/Tiles/Walls: a GM feature request to make "clicking any part of the geometry of a Scene Region control the entire Scene Region" was filed against core Foundry and closed `wontfix` (foundryvtt/foundryvtt#10755). The supported way to reselect an already-placed region is the **Region Legend** — click the "Régions" tool in the left-hand scene controls (this both activates the Regions layer and opens the legend), then click the region's name in that list; only then does `canvas.regions.controlled` populate, exactly what `trap-detect.js`/`trap-disarm.js` already read via `canvas.regions?.controlled?.[0]`. A GM who instead clicks the region's visible shape on the map — the intuitive thing to do, since that's how every other placeable in Foundry works — gets nothing, which reads as "it worked when I first drew it (because the shape-creation tool leaves it selected/its config open) but never again afterward." The "Configurer une Zone (MJ)" macro (`macro/zone-configure.js`) papers over both the legend *and* the toolbar: reported directly by a GM whose scene controls didn't visibly label a "Régions" tool at all (theme/layout-dependent, and not something to guess at without a live session to click through) — if `canvas.regions?.controlled?.[0]` is already set (GM found and used the legend), it jumps straight to that region's behavior sheet; otherwise it falls back to listing *every* region on the active scene (`canvas.regions.placeables`) in a plain clickable-rows dialog, regardless of which layer/tool is currently active. Either path filters `region.document.behaviors` for our own types (`game.rpg.terrain.TERRAIN_TYPES` keys, or `zoneEffet`) and opens that behavior's sheet directly — skipping "open the region's generic Foundry config, then find and double-click the right behavior row" — falling back to the region's own native config only when a region carries more than one RPG behavior (or none), rather than guessing which one the GM meant.

**The same unclickable-shape problem also blocked *deletion*, not just configuration — the macro used to only ever open a sheet, never delete anything.** Since the region's geometry can't be clicked (above), and the Region Legend is the only other supported selection route (also finicky per-GM, per the same #10755 limitation), a GM with no reliable way to select a placed zone also had no reliable way to get rid of one — reported directly ("je ne peux que les modifier"). `zone-configure.js` now offers Supprimer alongside Configurer at both entry points: when a region is already selected via the legend, a small chooser (`DialogV2.wait`, Configurer/Supprimer/Fermer) replaces the old straight-to-sheet jump; in the no-selection fallback list, each row gets its own 🗑️ button next to the existing configure button. Delete asks for confirmation (`DialogV2.confirm` — irreversible, deletes the Region document and cascades its embedded behaviors) before calling `region.document.delete()`.

**Two different shapes for a status effect's stat modifiers coexist in this codebase, and only one is fully supported.** `status-effects.js`'s `applyEffect()` (the older path) stores `modsFlat`/`modsPct` as nested buckets (`{principales:{force,...}, defenses:{...}, ressources:{pvMax,manaMax}, regen:{pv,mana}, move:{vitesse}, initiative:{mod}}`, fixed key set per `ensureBuckets()`/`computeModsNumeric()`) — it silently drops any stat outside that fixed set, which notably excludes `toucherPhysique`/`toucherMagique`/`fatigueMax`/`podsMax`. The spell sheet (`item-spell-sheet-v2.js`'s `effectsUI[].mods`) never used that path at all: it writes a flat `{stat: {flat, pct}}` map straight into `actor.system.etatsActifs`, which `sumActiveEffectMods()` reads via `KEY_TO_BUCKET` — a superset that *does* cover all 18 stats offered in the sheet's own dropdown. `zone-effects.js` originally called the older `applyEffect()` for its "état appliqué" field, capped at a single flat vitesse number — extended to a full stat-mods editor (mirroring the spell sheet's UI, `ZoneEffectBehaviorSheet`'s `effectMods[]`) and switched to the flat-shape path (`modsToBuckets()` + `applyZoneStateEffect()`, a small local wrapper around `resistances.js`'s `applyResistances()`) specifically to get the same 18-stat coverage and resistance handling a spell gets — `resistances.js`'s own header comment already named "futurs pièges" as an anticipated consumer. Anything else that applies a status effect and reaches for `applyEffect()` should probably reach for this flat-shape pattern instead unless it genuinely only needs the older bucket's stats.

**`removeBaseTN` and `retraitMod` on the same spell effect just added together — a pure UI redundancy, not two independent knobs.** `remove-state-macro.js`'s removal check computes `finalTN = baseTN + equipMod + effectMod + stMod`, where `baseTN` comes from `removeBaseTN`/`removeDifficulty` and `stMod` is that same effect's own `retraitMod` — so exposing both as separate editable fields on ONE effect (as the spell sheet used to) just makes a GM do the addition themselves instead of typing the total directly into `removeBaseTN`. `retraitMod` only means something as a modifier *from a different source* — gear (`system.bonus.retraitMod`, still on `armor-sheet.hbs`) or another active buff granting it via `mods.retraitMod` (that stat was never actually wired into the spell sheet's stat-mods dropdown, so this path has been unreachable through the UI the whole time this comment has existed — not something this pass fixed, just noting it's not new). Removed the per-effect field from `spell-sheet.hbs`/`item-spell-sheet-v2.js`; the builder now hardcodes `retraitMod: 0` rather than reading the (now-absent) input, so a spell edited *after* this change sheds any stale value the next time it's saved — same "clean on next touch, no separate migration" approach as the `effectVitesseFlat` removal above.

**Granting a resistance/vulnerability was already fully built end-to-end in `resistances.js`, just never reachable from the spell sheet.** `applyResistances()` reads `state.resistance = {tag, effectKey, durationReduction, dotReductionPct, immune}` off *whatever effect is currently active on the actor receiving a new one* (`getStateResistances()`) — but nothing ever wrote that field from the UI, so a GM could only grant elemental resistance by hand-editing JSON. Added "6 · Résistance accordée" to the effect editor (`resistTag`/`resistDurationReduction`/`resistDotPct`/`resistImmune`, same element list as the effect's own Type/Élément field in section 1 but intentionally a *separate* selection — the buff granting the resistance and the element it resists are unrelated, e.g. a `magique`-tagged "Écaille de dragon" buff granting `feu` resistance), and `spells.js` now always attaches a `resistance` object to the state it builds (never conditionally — an empty one with `tag: null` is already inert on the reading side, since `computeResistanceFor` filters out any resistance with neither `tag` nor `effectKey` set, so there was no reason to duplicate that emptiness check here). `durationReduction`/`dotReductionPct` intentionally accept negative values too, not just positive: same fields, sign flipped, express a vulnerability (things of that type last longer / hit harder) instead of a resistance — `computeResistanceFor` was already sign-agnostic (it's how weather amplification piggybacks on this same math), the spell sheet just never had a reason to expose negative resistance before now.

**A `RegionBehaviorConfig` subclass sheet is exactly as themeable as any other window, but needs the same two-part treatment as everything else in this file** — `.rpg-sheet`/`.rpg-zone-sheet` added to `DEFAULT_OPTIONS.classes` (appended via `Array.isArray(super.DEFAULT_OPTIONS?.classes) ? ... : []`, never a bare `classes: [...]` — `mergeObject` doesn't merge arrays element-wise, so that would silently drop whatever base classes `RegionBehaviorConfig` itself needs) *and* on the template's own root element, plus `applyUiTheme(this.element)` in `_onRender`. `zone-behavior.hbs`'s bonus/malus editor reuses the spell sheet's `.fx-*` CSS wholesale (`styles/item-sheet.css`'s selectors now list both `.rpg-spell-sheet` and `.rpg-zone-sheet`) rather than duplicating it.

## Repo layout notes

- `module/sheets/*-v2.js` are the live ApplicationV2 sheets; the non-`-v2` files of the same name (`character-sheet.js`, `monster-sheet.js`, `item-weapon-sheet.js`, ...) are the old V1 implementations, unregistered but kept in-tree for reference.
- `templates/item/spell-sheet.hbs` (and its controller `item-spell-sheet-v2.js`) is the most heavily-loaded item sheet: damages[], restores[] (heal/mana/fatigue given back, mirrors damages[] with a `siphon` lifesteal % field), and effectsUI[] (bonus/malus/aura/DOT/HOT catalog) all live there, each with GM-editable grids that must stay hidden from non-owner players and a separate `playerInfo`-style read-only summary for the player view.
- `packs/*/[name].db` are newline-delimited JSON (NDJSON) compendium sources, hand-editable with a small Python script (`json.loads` per line, mutate, re-`json.dumps` per line) — this is how `packs/documentation/documentation.db` (in-game player/GM guides) gets updated. Don't hand-edit `packs/documentation/documentation.db` if Foundry has the world open locally and may have rewritten it (locally-modified `.db` blocks `git pull` — `git checkout -- packs/documentation/documentation.db` before pulling if this happens).
- **Editing a `.db` NDJSON source alone does not change what Foundry actually serves** once `packs/<name>/<name>/` — a *compiled* LevelDB pack directory (`CURRENT`/`LOCK`/`LOG`/`MANIFEST-*`/`*.ldb`) — exists alongside it, which it currently does for `documentation` and `loot-tables` (but not `macros-rpg`: nothing ever migrated that one, since the macro auto-installer in `init.js` creates world `Macro` documents straight from the JS source files and never reads the `macros-rpg` compendium at runtime). Foundry migrates a legacy NeDB `.db` pack into that LevelDB directory once, the first time it's loaded, and from then on reads the compiled directory directly — it never re-consults the `.db` file again. This is exactly how the "Aide-mémoire MJ — Toutes les formules" duplicate outlived its own fix: an earlier commit correctly stripped the trailing newline in `documentation.db` that had produced a phantom `!journal!null` entry (confirmed by inspecting the raw LevelDB bytes — a document cloning the last real entry's name with `_id: null` and empty `pages`), but never touched the already-compiled `documentation/` directory sitting right next to it, so the phantom kept shipping regardless of how clean the source was. `loot-tables/loot-tables.db` had the mirror-image problem: emptied to fix a prior "remove the reference compendium" request, while its compiled directory kept serving a leftover entry the empty source no longer had. To actually change what a compendium with an existing compiled directory serves, you must rebuild that directory from the corrected `.db` source — editing the source is necessary but not sufficient. `@foundryvtt/foundryvtt-cli` (v3.0.4) is the right tool for this but has two bugs that break the obvious approach: `extractPack({nedb: true})` unconditionally *also* runs the ClassicLevel extraction branch against the same `src` path, which isn't a valid LevelDB and throws (`Iterator is not open: cannot call next() after close()`); and `compileClassicLevel`'s post-write `compactRange` call leaves the pack reading back completely empty on the very next fresh open (reproducible: compile, then open a separate process against the same directory — zero keys). Driving the `classic-level` package directly and skipping that optional manual-compaction step (it's an SST-merging optimization, not required for correctness) works reliably — that's how both packs were rebuilt.
- **Re-confirmed (2026-08-03) the `documentation` compendium duplicate fix is still intact in-repo**: opened `packs/documentation/documentation/` directly with `classic-level` (installed ad hoc, `npm install classic-level --no-save` — no `package.json` here means each unrelated ad hoc install can prune the *other* one as "extraneous" since neither is declared anywhere; reinstall `handlebars` afterward if template checks start failing with `MODULE_NOT_FOUND`) and read every key back: exactly 5, one `!journal!RPGDocFormules001` for "Aide-mémoire MJ", no phantom. A report of the duplicate still showing up in an actual running world therefore points at that world's Foundry install not yet running these already-fixed files (stale deploy), not a regression here — don't re-attempt the LevelDB rebuild described above without first re-checking like this, since it may well already be correct. Gotcha hit while checking: `ClassicLevel#open()` rewrites `CURRENT`/`LOG`/`LOG.old`/`MANIFEST-*` as a normal side effect even when only *reading* — it is not a read-only operation despite doing no writes of your own — so `git status` afterward, and `git checkout --`/`git clean` the pack directory before considering the tree clean again.
- **The "Aide-mémoire MJ" journal was never actually a duplicate at the data level — it had zero pages, so it rendered as empty, and a GM misread "empty + an unrelated ghost row" as "two of the same broken thing."** Reported (2026-08-03): one copy empty, the other "buggy" and un-openable/un-deletable, throwing `Compendium._onClickEntry`'s `Cannot read properties of undefined (reading 'sheet')` on click. Checked the raw NDJSON and the compiled LevelDB pack directly (both, independently) — there has only ever been **one** `!journal!RPGDocFormules001` entry, and its real bug was a legacy V9-era shape: `text.content` (6118 chars of real formula content) sitting directly on the JournalEntry document instead of inside a `pages[]` child, which Foundry V10+ simply doesn't render (a JournalEntry with an empty `pages` array shows as blank, regardless of what's parked in an unrecognized `text` key) — that's the "first one is empty." Fixed by moving that content into a proper page (`pages: [{_id, name: "Formules", type: "text", text: {content, format: 1}, title: {show:true, level:1}, sort:0}]`, mirroring the shape the other two working journals already use) in both `documentation.db` (careful not to reintroduce a trailing newline — see the phantom-`!journal!null` note above) and the compiled pack directory (`db.put()` for both the parent key and its own flat `!journal.pages!<parent>.<page>` key — LevelDB compendiums store embedded pages both ways, confirmed by reading an existing working entry's page key directly). The second, un-clickable "buggy" row is a **different animal entirely**: its Foundry-core crash signature (index shows a row; resolving the actual document behind it returns `undefined`) is the classic symptom of a client- or world-side stale/orphaned collection index, not pack content — and there is no second entry anywhere in this repo's git history, NDJSON source, or compiled pack to have caused it. Same client-reported symptom (un-openable, right-click-delete does nothing) for the "Terrain (MJ)" macro duplicate too, which independently confirmed it's not a `packs/` issue at all (Macros aren't compendium-backed — they're plain world documents the installer creates directly). Both point at the *live world's own* document/index state being out of sync with reality, entirely outside this repo — a `git pull` on system files can't touch it. Next step if this recurs: hard-refresh (not just reload the world) to rule out a stale client-side collection cache, then a full Foundry **server** process restart (not just closing the browser tab) to rule out a stale server-side one; if the ghost survives both, the world's own data store has an orphaned reference that needs direct inspection on that machine, which isn't reachable from this repo/session.
- **Found the actual reason "Terrain (MJ)" kept coming back / stayed un-deletable: the macro install-and-cleanup block in `init.js`'s `ready` hook never actually checked `game.user.isGM`**, despite its own header comment claiming "GM uniquement" — it ran on every connected client, GM or player, and once per browser tab. Two clients (two GMs, or the same GM in two tabs, or even a player's client) hitting the create-if-missing loop at the same time can both decide "doesn't exist yet" before either has finished creating it — a plausible origin for how a name like "Terrain (MJ)" got duplicated in the first place, well before it was ever removed from `MACRO_DEFS`. It also broke the orphan-cleanup guard added for the "don't delete a macro whose sheet is open" bug: `m.sheet?.rendered` only reflects state in *that specific client* — a second tab (or a second GM) has no way to see that another client has the document's `MacroConfig` open, deletes it anyway, and the tab with it open then throws exactly `You must provide an _id for every object in the update data Array` the instant that GM clicks Save (reported again, same error, same stack shape, after the sheet-open guard had already shipped) — because the document was deleted out from under an editor that had no way to know. Gated the whole block behind `game.user.isGM && game.user === game.users.activeGM` (the standard Foundry "elect one GM to run this" pattern) so it runs at most once per world-load instead of once per connected client. Doesn't fully close the same-GM-two-tabs case (`activeGM` picks a *user*, not a specific tab), but removes the far more common multi-client race entirely. If this error reappears: close the stale macro sheet without saving and reload — the delete already succeeded, the open form is just pointing at a document that's gone.
- **Emptied the `documentation` compendium entirely (2026-08-03), same treatment as `items-reference`/`monsters-reference` before it.** Despite the content-shape fix and the `activeGM` gate both landing and being confirmed present on the GM's actual deployed files (verified via `git status`/`ls` on their machine post-pull — the right `.ldb` generation was there), the GM still saw duplicate/empty/un-openable journal entries even after a full Foundry application restart on their end. Three sessions of "fix the pack, confirm it's clean, GM still sees it broken" without ever reproducing the corruption directly is a strong enough signal that whatever's wrong lives in Foundry's own compiled-pack handling on that machine (possibly platform-specific — this was rebuilt/verified exclusively on Linux via `classic-level`, never round-tripped through a real Foundry-on-Windows load) and isn't practically debuggable from this repo/session. Rather than attempt a fourth pack rebuild blind, moved the three documents to plain **world** JournalEntries instead (GM pastes them once via a `JournalEntry.create({name, pages})` console snippet built from the last-known-good NDJSON content) and truncated `packs/documentation/documentation.db` to empty + deleted the compiled `packs/documentation/documentation/` LevelDB directory, exactly the same mechanism as the two earlier "GM will author their own instead" empties — confirmed no other pack or rule module references `Compendium.rpg.documentation.*` UUIDs first (only `unlock-compendiums.js`'s generic pack-unlock list names the pack id itself, not any entry inside it). The `documentation` pack registration stays in `system.json` so the compendium tab still exists, now just empty — same reasoning as the other two.
- **The real, final answer on "Terrain (MJ)": it was never a world Macro at all — it was sitting in the completely dead `macros-rpg` compendium, `packs/macros/macros.db`.** All the world-Macro-side work above (the `activeGM` gate, the sheet-open guard, the orphan cleanup) was chasing the wrong document class the whole time — confirmed only after the GM explicitly reported "c'était le double qui est toujours là" (the click that threw `Compendium._onClickEntry`'s `Cannot read properties of undefined (reading 'sheet')` was on a *Compendium* entry, not a world Macro).
